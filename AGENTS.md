# BLIS System Agent Quick Guide

This file is for coding agents. Keep it short, execution-focused, and updated when behavior changes.

## Project Snapshot

- Root app: Laravel 12 API + server-rendered entry.
- Frontend app: Vue 3 SPA in `frontend/` (Pinia + Vue Router + Axios).
- Auth: a Laravel Sanctum token kept in an HttpOnly, SameSite=strict cookie (`auth_token`, set by `AuthTokenCookieService`). With "Remember me" ticked at sign-in it lasts 7 days; unticked it is a session cookie (gone when the browser closes) and the token is refused after 8 hours unused, for every role. An open tab's background refreshes count as use on the server, so the page also signs itself out after 8 hours without a press, key or scroll (`frontend/src/utils/idleSignOut.js`, limit sent as `session_idle_minutes`). Tests: `tests/Feature/RememberMeSignInTest.php`. The SPA holds no token of its own; `frontend/src/api/http.js` sends the cookie with `withCredentials`.
- Database: MySQL in Docker.

## Role and Access Rules

- Canonical roles:
  - `student`
  - `staff_master_examiner` (teacher/faculty-equivalent)
  - `admin`
- Public registration always creates `student` (`POST /api/auth/register`). Its `admission_year` is the current school year (by the school calendar, below) minus the year level plus one, so a 1st year signing up in January 2027 gets 2026, not 2027.
- Sign-in page, "Resend verification email" (`LoginView.vue`): 20 seconds between one resend and the next, and the fourth press within an hour for one address says "Too many attempts. Try again later." without being sent. The times are kept per address in `sessionStorage`; the server's own limit (3 an hour per mailbox, the `verification` limiter) is what the count mirrors, and its 429 shows the same message.
- A sign-up holds its email and student ID only once it is verified. `POST /api/auth/register` replaces any account matched by `User::scopeUnclaimedRegistrations()` (unverified student, untouched since it was created, no rooms or results) instead of answering "already taken", and `registrations:prune-unverified` removes those whose link expired, hourly. An account an administrator has edited never matches. Tests: `tests/Feature/RegistrationEmailVerificationTest.php`.
- Management behavior checks include:
  - Backend: `admin`, `staff_master_examiner`, and legacy `faculty` string.
  - Frontend: same set for management sidebar.
- Admin-only modules:
  - User management (`/api/admin/users`). `PATCH /api/admin/users/{user}` takes `email_verified` (boolean): an administrator vouching for an address in place of the emailed link, for someone who cannot open it. Taking it back signs the account out; an administrator cannot unverify themselves. On the Users page: a Verify button on rows still "Pending", and an "Email verified" box in the Edit dialog. Accounts an administrator creates are verified from the start. In the Create / Edit User dialog the Role comes first, and Student ID, Year Level, Status and Admission Year show only for a student; turning a student into staff says first that their student ID, year level and status go (the server clears them).
  - Audit logs (`/api/admin/audit-logs`, page `admin/AuditView.vue`). Read through `App\Services\AuditLogBrowser`: filters `q` (description, action, IP, actor name or email), `category` (groups in `App\Support\AuditEvents::CATEGORIES`, by action prefix), `outcome` (`failure` = `auth.login_failed`), `actor_id`, `target_type` + `target_id`, `from` / `to` (instants; the page sends the ends of the reader's own days). Each row comes back with `event` (a readable name from `AuditEvents::LABELS`; give a new action one there), `target` (`App\Support\AuditTargets` names it, or falls back to the name saved in the entry's metadata once it is deleted), `device` and `user_agent`. `GET /api/admin/audit-logs/export` is the same filters as CSV (up to 50,000 rows, times in `tz`, cells starting `= + - @` written as text) or, with `format=xlsx`, as an Excel file with sized columns and a frozen, filterable heading row (the newest 5,000 rows: PhpSpreadsheet builds it in memory, about 95 MB at that size against the server's 256 MB). A CSV carries no column widths, which is why Excel showed its times as ########. Both record `audit.export` with the format. The page offers "Export Excel" and "CSV". Sign-ins are logged (`auth.login`, `auth.login_failed` with what was typed as the identifier and why, never the password; `auth.logout`). Nothing edits or deletes an entry. Tests: `tests/Feature/Admin/AuditLogPageTest.php`.
  - Global room oversight (`/api/rooms` for admin, or `/api/admin/rooms`). In any room an administrator sees what its teacher sees: `GET /api/rooms/{room}` returns the room's current and archived exams with "n / m submitted", and `GET /api/exams/{exam}/live-dashboard` answers an administrator for any exam and room (a teacher still only for their own).
- An administrator can also do everything a teacher can, over every teacher's work, so the school can step in for a teacher who is away. In the controllers (base `App\Http\Controllers\Controller`, backed by `RoleService`): `$this->canTeach($user)` (teacher or admin) gates the teaching routes, and `$this->oversees($user, $ownerId)` answers "may this person act on something of `$ownerId`'s" (the owner, or an admin); `$this->oversees($user)` with no owner means "sees everybody's" and is what the list routes filter on. Use those two in a new teaching endpoint. What an admin creates belongs to the admin; changing a teacher's exam or file does not take it over.
  - Reports: `GET /api/reports/overview` is programme-wide for an admin and takes `?teacher_id=`; it then answers `scope` (`teacher_id`, `teachers`). The analytics queries ask `User::overseesAllTeaching()` before narrowing to an owner, and `DashboardAnalyticsService::asOwner()` is how one person's are picked out.
  - Audit: `$this->recordAudit()` (`AuditLogService::recordAction()`) adds `owner_id`, `owner_name` and "(belongs to ...)" when an admin acts on a teacher's room, exam or Library file. A route that has already deleted the thing passes `owner_id` in the metadata.
  - Pages: the admin's sidebar has Administration and Teaching headings (`dashboardNavGroupStarts`), and its menu scrolls with the account tile pinned. Exams, Library, Review Bot and the exam form show "By <teacher>" to an admin, and Exams, Library and the Dashboard take a teacher filter (`shared/OwnerFilter.vue`, `utils/owners.js`). Tests: `tests/Feature/AdminTeachingAccessTest.php`.

## Phone and Tablet Layout

- Breakpoints live in `frontend/src/views/dashboard/composables/useViewport.js`: `useCompactLayout()` (≤900px: sticky app bar + slide-over nav drawer in `DashboardLayout.vue`) and `usePhoneLayout()` (≤640px: rows instead of cards/tables).
- A page moves its main action into the app bar with `<Teleport to="#layout-topbar-actions" defer :disabled="!isCompact">`; its duplicate title header carries `.room-page-head.is-page-title` so it hides at ≤900px.
- The Rooms pages' state is `composables/useRoomsModule.js` (rooms, membership, dialogs), built from `useStudentExamAttempt.js` (taking and reviewing an exam), `useRoomLiveBoard.js` (the teacher's live board) and `roomsHelpers.js`. The largest views keep their styles in a sibling file (`roomsView.css`, `examsView.css`, ...) loaded with `<style scoped src>`.
- Phone filters and per-row actions use `frontend/src/components/BottomSheet.vue`; rows use `.directory-row` / `.directory-row-details` in `dashboard/styles/16-phone-layouts.css`.
- Touch screens (`pointer: coarse`) get 44px controls via `--control-height` and 16px field text (iOS zooms into smaller fields).
- A list that is a table on desktop switches on the page's measured width, not the window's (the sidebar takes 264px): `useElementWidth()` in `useViewport.js`. Exams falls back to `.directory-row` rows under 860px, Library to cards under 940px, Licensure to rows under 940px. Students has three steps: rows under 920px, an eight-column table up to 1599px (email, batch, status and last activity folded under their neighbours, each still sortable from the heading it folded into), all twelve columns from 1600px. Users: rows under 950px, icon-only row buttons up to 1139px. Do not give a table a `min-width` and let its action column scroll off-screen (the shared `.directory-table` rule sets 1080px; a table that needs less resets it).
- A view whose layout decides what it fetches (Users: rows load more, the table pages) passes `estimatePageWidth()` to `useElementWidth()` so the first request already matches the layout.
- Dialogs: on phones every `.modal-card` is a bottom sheet (`margin: auto 0 0`, padding from `--modal-pad`); the exam form is full screen. From 641px a dialog is never taller than the screen: it scrolls inside and its `.modal-actions` stay at its bottom edge. `DashboardLayout.vue` locks page scroll while any `.modal-backdrop` or `.exam-attempt-backdrop` is in `<body>`, and drops a click on a backdrop whose press began inside the dialog (a text selection dragged out used to close the dialog). The exam form ignores a click outside it once anything in it has changed (`dismissExamModal`). Dialog-specific layout goes in the owning view's own `<style scoped>`, because the single-class `.modal-card` rules late in `dashboard.css` override earlier ones.
- Never put `min-height: 0` on rows inside a list with a `max-height`: the rows collapse to their padding once they no longer fit (this was the overlapping room list in the exam form).
- The exam a student is taking (`.exam-attempt-*`, in `dashboard/styles/13-exam-overlay.css`; the question list, review screen and shortcuts are in `17-exam-palette-review.css`; its logic is `composables/useStudentExamAttempt.js`): its header and buttons are pinned, so their height comes out of the question. Up to 640px the header is one row (64px) and the buttons two (113px); from 641px one row each. Measure both before adding anything to either. From 901px there are no boxes around the question or its buttons: the question, its choices and the Bookmark / Previous / Next row (Next filled) are one centred column, `clamp(720px, 58vw, 1120px)` wide so a line stays readable, and its type, choices and buttons are sized with `clamp()` against the screen; a line of key hints sits under it; Submit sits under the question list there, away from Next (`.exam-sidebar-submit`). The question list says only answered (filled navy) or not (white, outlined), with a gold ring on the current question and the gold corner on one marked for review; no red while the exam is under way (an unanswered question is not an error, and red against green is the pair colour-blind students lose). It has All / Unanswered / Marked filters, and from 41 questions smaller cells (`.is-dense`, never under about 34x32px with 13px numbers, the low end of what exam programs use) so about 96 show on a full-HD screen and the rest after a short scroll. "Bookmark" is called "Mark for Review" on screen (still `is_bookmarked` in the data). Submitting goes through a review screen (`examReviewOpen`): Next on the last question ("Review Answers"), "Review & Submit" under the list, or "Finish" on a phone open it; it lists unanswered and marked questions, and only its Submit Exam opens the confirmation. Keys (`handleExamKeydown()` in `RoomsView.vue`): left/right and Enter move between questions, up/down or a choice's letter pick the answer; Enter on the last question opens the review screen and never submits; on the review screen only left arrow or Escape (back) do anything; `?` shows the shortcuts list (and closes it); there is no link to it on screen, as most exam sites have none. None of them act while typing in a field, on a focused button's Enter/Space, or with a dialog or the phone's question list open. A key pressed while an answer is still saving is acted on once it has saved. Its text cannot be selected, copied, cut, dragged or right-clicked (`.exam-no-copy` in `dashboard.css`, `blockExamCopy()` in `RoomsView.vue`), so questions are not pasted into a search; an input or textarea inside it still works. A screenshot or a phone camera is not stopped by this.
- A row that scrolls sideways with its scrollbar hidden (tabs, filter chips) takes `v-scroll-hint` (`frontend/src/utils/scrollHint.js`), which fades the edge that has more beyond it.
- The Rooms pages and the Review Bot pin themselves to the screen height only where that leaves their lists room: Rooms from 1201px wide and 700px tall, Review Bot from 1001px wide. Below that the page scrolls. A 1366x768 laptop shows about 640px of page height, so check fill-screen layouts at 1366x640, not 1366x768; a 1920x1080 screen at 125% scaling shows about 1534x728, which is why the Rooms limit is 700 and not higher (there the three columns must end on one line).
- No text under 11px. The trend chart (`ScoreTrendChart.vue`) draws at its real width so its labels are not scaled down with it, and `JsChart.vue` wraps the category names of a sideways bar chart.
- `GET /api/admin/users` returns rows in directory order (current students by year, archived by year, staff, admins; then name) plus `group_totals` for the headings; phones grow the list with `per_page` instead of paging. `GET /api/admin/audit-logs` pages with `page`/`per_page` (legacy `limit` still works) and returns `meta`.

## Staying Current Without a Reload

Nobody should have to reload a page to see what changed. Four pieces keep that true; a new page or feature has to use them rather than work around them.

- **Time** (`frontend/src/utils/clock.js`): anything on screen that depends on the time (has an exam opened, has it closed) reads `now()`, never `Date.now()`, and names the moment its answer changes with `beatAt()`. `now()` is reactive and follows the server's clock (learned from the `Date` header in `api/http.js`), so Take Exam turns on at the start time by itself, even on a phone whose own clock is wrong.
- **Data** (`frontend/src/utils/liveRefresh.js`): every page module calls `useLiveRefresh(quietRefresh, { every, when })`. All of them refresh when the reader comes back to the tab; the pages people wait on also refresh on a timer: student and staff Rooms and student Home every 60s, Audit every 60s, the announcement banner every 5 minutes. A quiet refresh sets no loading flag, clears no message, keeps the selection, and leaves the data alone if it fails: that is what `{ silent: true }` on a load function means. `when` keeps it out from under an open dialog and out of an exam.
- **Cost**: the student Rooms timer is one `GET /api/rooms/{id}` a minute per student, spread at random over the minute. That is the page a whole class sits on before an exam; do not shorten it or add requests to it without redoing that sum.
- **Updates** (`frontend/src/utils/appVersion.js`): a tab opened before a deploy runs old code and would ask for page scripts the deploy removed. The site's `index.html` is compared with the running one every 5 minutes and on return to the tab; once it differs, the next move to another page is a full load. A page script that fails to load anyway triggers the same at once. Not active under `npm run dev`.
- **Sessions** (`frontend/src/api/http.js`, `main.js`): a 401 from anything outside `/auth/`, or the 403 "Account is disabled.", sends the reader to `/login?ended=...` through the router, where the page says why.
- A save or delete reloads what it changed itself (every module already does); `useLiveRefresh` is for changes made by someone else.
- **Background jobs**: a page waiting on a queued job asks the server whether the job is still going rather than guessing from what has arrived. Review Bot generation saves its drafts a batch at a time, so `GET /api/library/review-bot/questions?source_bank_id=` returns `generating` (the run's in-flight lock, `ReviewBotAdminService::isGenerating()`), and the generator page re-reads its list every 4s for as long as that is true, including after the page is left and reopened. The Library's topic tagging does the same from each bank's `mapping_status`.

## Visual Design

- One look for the whole app, set by the signed-out pages: Poppins (`--font-display`, served from the site itself through `@fontsource/poppins` in `main.js`; the production CSP blocks Google Fonts), the navy panel (`--panel-navy`), large radii (`--radius-sm/md/lg` = 10/16/22px), white cards on the cream page, and navy buttons with gold text. Tokens live in `frontend/src/style.css`.
- Signed-out pages share `frontend/src/views/auth/AuthLayout.vue` + `auth.css`; logos are in `frontend/src/assets/`.
- Dark mode: `frontend/src/utils/theme.js` sets `data-theme='dark'` on `<html>` (choice `light` / `dark` / `system`, kept in `localStorage` as `blis-theme` and in `users.preferences.theme`, which wins once signed in; `public/theme-boot.js` applies it before the page draws, so there is no white flash; it is a file because the CSP allows no inline script). Light is the default. Most colours are written straight into the CSS, so `frontend/scripts/dark-theme.mjs` wraps each one as `var(--dk-<role>-<colour>, <colour>)`: light mode never defines `--dk-*`, so it draws exactly the old colour, and `src/theme/dark-colors.css` (generated) defines them all for dark. The role comes from the property: `bg` (a white card turns dark, a navy button stays navy), `fg` (navy text turns light, white text stays), `line`, `shadow`, and `glow` (a translucent colour inside a radial-gradient, dropped in dark). Light surfaces snap to a few fixed levels (`SURFACE` in the script: page `#11141c`, card, inset, raised, one border), as common dark themes do, rather than one near-black per near-white; pastel fills become a faint wash of their hue. The unambiguous tokens (`--ink*`, `--surface*`, `--border-*`, `--lnu-text*`, shadows) are redefined by hand in `style.css`'s `:root[data-theme='dark']`. After adding CSS with a colour, run `node scripts/dark-theme.mjs` in `frontend/` (`--check` lists any colour without a dark value); hand-tuned values go in its `OVERRIDES`. Chart.js draws on a canvas, so `JsChart.vue` keeps a light and a dark palette and redraws when `activeTheme` changes. PDFs and emails stay light.
- Dashboard pages get the look from the "BRAND LAYER" (`dashboard/styles/12-brand-layer.css`) (shared primitives: `.surface-card`, `.primary-btn`, `.text-input`, `.pill`, tables, modals). Restyle there before adding per-page CSS. `dashboard.css` is loaded once, unscoped, by `DashboardLayout.vue`, and is only a list of `@import`s of `dashboard/styles/01-...17-*.css` in cascade order (a later file overrides an earlier one, so keep new rules in the file of their topic and mind the order) (it used to be a `<style scoped src>` in 25 components, 3.5 MB of CSS in all); do not add it back to a component. A component's scoped rule beats a `dashboard.css` rule of the same classes, so a broad descendant rule (`.row span`) will also restyle the pills and buttons inside it: use `>` or a class.
- Charts: `frontend/src/components/charts/JsChart.vue` wraps Chart.js (bar and line, pass-mark line, value labels, tooltips) and is used on the teacher dashboard and the Licensure page. Below-passing is amber `#c98a1e` and passing is indigo `#3949ab`, a pair checked for colour-blind separation; do not swap in red/green. A line chart with two or more datasets is a comparison: no area fill, straight segments, filled markers with a surface ring, a line key per series in the tooltip; a dataset may be `dashed` and carry `details` (a phrase per point for the tooltip), and the page draws the legend in HTML. The passing-rate trend's pair, LNU indigo `#3949ab` (dark `#7f8ce0`) and National magenta `#d55181` (dashed), was checked with the dataviz palette validator in both themes; amber stays reserved for below passing. `ConfidenceGauge.vue` is a hand-built SVG gauge.
- Subjects get no colour of their own. The student Review Bot (`student/ReviewBotView.vue`) is white panels with navy for what is chosen: subjects are two columns of short names, white and navy once picked, like the other chips; the score box is neutral whatever the score. An earlier per-subject palette was taken out at the user's request as too colourful.
- Explanations sit behind an (i), not in a paragraph: `frontend/src/components/InfoTip.vue` (`text`, `label`, `on-dark` on the navy panels) beside a heading or field label. Hover or keyboard focus opens it on a desktop, a tap on a touch screen; Escape, a tap elsewhere or scrolling the icon away closes it, and screen readers read the text with the icon. The page subtitles from `dashboardNavigation.js` are one, by the title in `DashboardLayout.vue` (also on phones). Keep on the page, not behind an (i): errors and warnings, what someone must do next, privacy notices (what Feedback sends), consequences before acting (the password card, Hidden/Visible results, the end-time choice, Library subject change), empty-list messages, the End of School Year page, and everything in the exam a student is taking. A heading that phones hide (`.is-page-title`) is no place for one.
- Forms say what they will not accept under the field (`frontend/src/utils/fieldChecks.js`: checks mirroring the controllers' rules, and `useFieldChecks()`; `components/FieldError.vue` for the line under the field; the red edge is `.text-input.is-invalid`). A problem shows when the reader leaves the field or presses the button; one that more typing cannot fix (a letter in a student ID, a number over the limit) shows as they type. Buttons stay enabled and point at what is missing when pressed, rather than sitting greyed out without a reason. A save's own error is shown in the dialog that made it, and a 422 under the field it names, never only on the page behind the dialog. A new form uses these.
- Any `display: grid` list that can hold a long one-line string needs `grid-template-columns: minmax(0, 1fr)`, or the row widens the page on phones.

## Docker/Runtime Notes

- Service ports:
  - App (nginx): `http://localhost:8080`
  - phpMyAdmin: `http://localhost:8081`
- The `queue` service runs Laravel background jobs, including AI item mapping. Bank save/import now queues classification instead of waiting on OpenAI inline.
- Server errors are emailed to the developers (`App\Support\ErrorAlerts`, hooked in `bootstrap/app.php`): only what Laravel reports (no 4xx), one email per distinct error every 15 minutes, never the request body, sent after the response. Address `ERROR_ALERT_EMAIL`, else `FEEDBACK_DEVELOPER_EMAIL`; none locally unless `ERROR_ALERT_IN_LOCAL=true`. Logs rotate daily and are kept 14 days (`LOG_STACK=daily`). Tests: `tests/Unit/Support/ErrorAlertsTest.php`.
- MySQL container is intentionally named `lnu_lle_db`.
- MySQL volume name is `blis_system_mysql_data`.
- Production (lnu-blis.live) deploys itself: a merge to `main` is live within a few minutes. The server runs `scripts/auto-deploy.sh` (installed as `~/auto-deploy.sh`) from cron every minute; on a new commit it waits until no exam attempt is running, then runs `~/deploy.sh` (backup, pull, rebuild, migrate). So a migration merged to `main` runs on real data straight away: try it on MySQL 8.4.8 first. Its log is `~/auto-deploy.log` on the server; a failed commit is not retried until `~/.failed-commit` is removed or another commit lands. After changing the script, copy it to `~/auto-deploy.sh` again.

## Common Commands

- Start stack: `docker compose up -d`
- Start or restart the queue worker after compose changes: `docker compose up -d queue`
- Stop stack: `docker compose down`
- Reset DB schema + reseed: `docker compose exec -T php php artisan migrate:fresh --seed`
- Seed only: `docker compose exec -T php php artisan db:seed`
- Run migrations: `docker compose exec -T php php artisan migrate`
- Watch queued job logs: `docker compose logs -f queue`
- Re-check scoring by hand: `docker compose exec -T php php artisan scoring:export` (30 submitted attempts, seed 1; `--count`, `--seed`, `--exam=`): two CSV files under `storage/app/private/scoring-check/`, every dealt item with its key, the answer and the stored result, and each attempt's stored score beside the score worked out from the key. Tests: `tests/Feature/ScoringExportTest.php`.
- Install PHP deps in container: `docker compose exec -T php composer install`
- List users/roles quickly:
  - `docker compose exec -T php php artisan tinker --execute="dump(App\\Models\\User::select('id','name','email','student_id','role')->get()->toArray());"`

## Known Fast Fixes

- Error: `vendor/autoload.php` missing
  - Run `docker compose exec -T php composer install`
- 500 with storage/log permission denied
  - Run:
    - `docker compose exec -T php sh -lc 'mkdir -p storage/logs bootstrap/cache && chown -R www-data:www-data storage bootstrap/cache && chmod -R ug+rwx storage bootstrap/cache'`
- Container name/port conflicts with old projects
  - Check `docker ps` and remove conflicting containers before `up -d`.
- 429 `Too Many Attempts`
  - Limits live in `AppServiceProvider::configureRateLimiting()`. Per-IP tiers are sized for a campus behind one address (about 230 students): 120 sign-ins and 600 signed-out requests a minute, 30 registrations a minute and 150 an hour, 30 resend/reset emails an hour. The tight tiers are per account (5 sign-in tries a minute) and per mailbox (3 emails an hour). Signed-in users are counted per user (120 a minute). Covered by `tests/Feature/CampusRateLimitTest.php`.
- New backend modules (API-backed):

Inputs: exam type (pre-test or mock board; a retrained version with battery rows also has battery, as one 0/1 input per type, `LogisticModel::examTypesFor()`) and the six subject scores. Version 1 was trained in WEKA (`ml/models/logistic-v1.*`) and is loaded into `let_models` by the migration `2026_11_03_000000_rebuild_let_models_for_logistic_regression`; the app computes from the stored coefficients (`LogisticModel`), never the `.model` file (no Java on the server). A missing score is filled with the training mean, as WEKA's ReplaceMissingValues does. "At risk" means P(FAILED) ≥ 0.25 (`LogisticModel::AT_RISK_CUTOFF`), decided on the unrounded probability.
    - What a student sees (`BoardExamOutlook`, the `components/EstimatedOutcome.vue` card on Analytics and on the staff Student Profile; tests in `EstimatedOutcomeTest.php`): locked ("Your Estimated Outcome appears after you finish all six subjects of a pre-test or mock board.") until the student has a submitted sitting of all six subject exams of one pre-test or mock board series; any series under way shows what it still needs. Then the most recently completed series is read: the chance of passing, "At risk" / "Not at risk", which series, and its six scores, with the note that it is an estimate for review planning. The same wording for every year level. Battery and regular exams never feed the student's card. An exam sat twice counts by its latest sitting (`ReviewSeriesFeatureBuilder`).
    - Early estimate from battery exams (`BatteryEarlyEstimate`, staff only: `early_estimate` in `GET /api/students/{student}/analytics`, never in the student's own analytics): it turns itself on with the model in use. `off` unless the active version has `battery_ready` (and a battery input); `superseded` once the student finishes a pre-test or mock board series; otherwise the latest complete semester of battery exams from the 3rd year on (`BatterySemesterFeatureBuilder`, the same rows the model learnt from) with exam type `battery` (`ready`), a later semester short of a subject shown as `pending`, `locked` with only short semesters, `none` without any. On the staff Student Profile it takes the Estimated Outcome card ("Early Estimate", `describeStaffReadiness()` in `composables/readiness.js`) while that is locked; the Licensure page says whether early estimates are on. Tests: `tests/Feature/BatteryEarlyEstimateTest.php`.
    - Retraining (`LetModelTrainer`, `RetrainLetModelJob` on the queue; tests in `LetModelRetrainingTest.php`, `LogisticTrainingTest.php`, `BatteryTrainingRowsTest.php`, `BatteryTrainingTest.php`): only when an administrator clicks "Retrain model" on the Licensure page, and only with 10 confirmed LLE results the last training did not have. Nothing retrains by itself. Rows are every row of the base dataset plus, for each graduate with a recorded pass or fail (not demo accounts, first sitting only; did not take is never a label), one row per series they completed before their LLE date (no date: Dec 31 of the exam year), and one row (exam type `battery`) per semester of battery exams sat before that date from their 3rd year on (the semester's school year minus `admission_year`, plus one; none without an admission year) that covers all six subjects (`LetTrainingSetBuilder`, `BatterySemesterFeatureBuilder`: a semester is the exams' `school_year` + `semester`, each subject the percent right over every item dealt in that semester's battery exams, latest sitting of each, a blank wrong, an item's subject its question's). The ridge is picked as CVParameterSelection picks it (`RidgeSelector`), and the version is judged by 10-fold cross-validation repeated with seeds 1 to 10, pooled per repeat then averaged, ridge picked again inside each training fold, ZeroR on the same folds (`LetModelEvaluator`, `WekaFolds`, `JavaRandom`). It goes into use only if, on its pre-test and mock board rows (`by_type.review` of the evaluation; every row without battery rows), ROC area ≥ 0.70, FAILED recall ≥ 0.60 at the cutoff (`LetModel::TARGET_*`), Kappa above ZeroR's, and ROC area at least the live version's; otherwise it is kept, inactive, with the check it failed. The stored `roc_area` ... `zero_r_kappa` are those review-row figures. Its battery rows are judged apart (`battery_*` columns, `battery_checks`): `battery_ready` only when they reach both targets and beat ZeroR on their own and at least `LetModel::BATTERY_MIN_FAILED_GRADUATES` (10) graduates who gave them failed the LLE; it never decides whether the version is used. The Licensure page shows what battery exams would add (`data.battery_*`) and each version's battery figures. Each version is a row in `let_models` (figures, ridge, coefficients, cross-validation detail) with a file under `storage/app/private/let-models/`; an administrator can put any version that meets both targets into use. Routes: `GET /api/predictions/let/model` (staff and admin), `POST .../model/retrain` (202, queued) and `POST .../model/activate` with `version` (admin only). The Licensure page polls every 5s while a training runs.
    - The trainer, the ridge choice and the cross-validation give the same coefficients and figures as WEKA (to 1e-4). After changing any of them, rerun the checks in `ml/README.md`; the test suite alone does not prove that.
  - Library import (`POST /api/library/import/preview`, `app/Services/Library/DocxQuestionParser.php`, which runs the four steps in `app/Services/Library/Docx/`: `DocxLineReader` reads the file into lines and marks, `AnswerKeyReader` finds a key, `QuestionSegmenter` cuts the lines into questions (`buildQuestions()`), `AnswerMarkResolver` decides which mark means correct (`resolveMarkedAnswers()`)): the correct choice is read from however the teacher marked it, not from one colour. Each choice records the marks on it (highlighter, shading, a text colour, bold, underline); `resolveMarkedAnswers()` then accepts a mark as the answer mark when it sits on exactly one choice per question across at least 5% of the questions (30% for bold and underline). A mark on two choices of a question sets no answer and warns. PhpWord does not read shading (`w:shd`), so `loadDocument()` parses a copy with shading rewritten as highlight. Tests: `tests/Feature/DocxAnswerMarkingTest.php`.
    - Core subject: the preview returns `suggested_subject`, detected from the questions. The Add Questions dialog (`LibraryView.vue`, `useLibraryManager.js`) shows it in a "Core Subject" field the teacher or administrator can change before saving; once they have picked one, picking another file does not overwrite it. What is in the field is what is saved.
    - Editing a question (`PATCH /api/library/questions/{question}`) changes its choices where they are, by `options.*.id`: students' exam answers point at them, and deleting and re-creating them (as it once did) erased which choice every student had picked. A choice picked in an exam cannot be removed (422 under `options`). When the correct answer changes, `ExamAttemptService::regradeQuestion()` marks every exam answer to it again and re-scores each attempt whose marks changed, handed-in ones included; logged `library.question.regrade`, and the reply says how many were re-graded. Tests: `tests/Feature/Library/QuestionEditKeepsAnswersTest.php`.
    - Editing a question's mapping (topic, subtopic, difficulty, cognitive level) is done per question in the set's question list: View on the row, or "Edit Questions" in the Edit Question Set dialog, which saves a changed name or subject first. Saved by `PATCH /api/library/questions/{question}`. The edit form is filled from `GET /api/library/banks/{bank}/questions`, so that list must carry everything the form saves: a field missing from it (the subtopic once was) is cleared by the next save.
    - Tagging taxonomy: the LLE Table of Specifications, `docs/lle_tos.json`, read by `App\Support\LleTaxonomy` and nothing else: 6 subjects under their official names, 29 topics, 154 sub-topics, each with its TOS code and `tos_items` (board questions; reference data), plus an "Other / Unclassified" topic per subject with no sub-topics. Old spellings ("Reference Services", "Library Management") are aliases; a set's subject is saved under the official name (`LibraryController::subjectToSave()`). Topic and sub-topic rows are created on first use (`QuestionMappingService::resolveTopic()` / `resolveSubtopic()`) with `code`, `tos_items` and `sort_order`, and are named code first ("2. Descriptive Cataloging", "2.4 Apply the rules…"), so every screen shows the code. A tag outside the TOS is refused (422, `tagProblem()`), on the Library and the Review Bot editors alike. Keywords: `TopicKeywordDictionary` (subject key → topic code → sub-topic code → `concept` + weighted phrases; written for faculty to review). Phrases are normalized exactly like question text (accents, punctuation, a dash between words) and also match a plain plural or singular. No keyword at all → "Other / Unclassified" (not sent to review for that); a best topic below 0.45 confidence → `pending_review`. Other counts toward the subject score, never as a topic in analytics or mastery, and is not a Review Bot topic. Generated Review Bot questions name a sub-topic by its `concept`, never by the competency statement. `php artisan tos:keyword-report` (`--bank=`, `--all-banks`, `--docx=`, `--subject=`, `--details`) counts per subject how many got a sub-topic, went to Other or await review, without saving. Tests: `tests/Unit/Support/LleTaxonomyTest.php`, `tests/Unit/QuestionClassification/LocalQuestionClassifierTest.php` (every phrase matches a question containing it), `tests/Feature/TosKeywordReportTest.php`.
    - Tag status: a tag the tagger was unsure of is `pending_review` until a teacher confirms it ("Confirm All Suggested Tags", or saving the question's own edit); the rest are `confirmed` as they are written. `GET /api/library/banks` returns `pending_tags_count` and `confirmed_tags_count`, and the Library's Topics column reads "N tags to confirm" or "Tags confirmed" from them once tagging has finished. In the question list each question shows "Tag pending review" or "Confirmed", and the set "All tags confirmed".
    - Answer keys: a section of single letters, or a key typed after the last question with no section break (`takeTrailingAnswerKey()`: lines of nothing but "1. d   26. c" pairs, or five or more one-letter lines). The key is held by question number. Where a marked choice and the key disagree the key is used and a warning says so; a key letter the question does not have falls back to the mark.
    - Cutting the file into questions (`buildQuestions()`, tests in `tests/Feature/DocxQuestionReadingTest.php`, each a layout from a real LNU exam): if the document numbers its questions (Word numbering, or three or more typed "12." lines) a question starts at a number and nowhere else; an unnumbered, unlettered line after a question's choices is left out with a warning instead of becoming a question or being glued to the last choice. The "looks like a question" guesses run only for documents with no numbering. A typed letter is a choice label by `CHOICE_LABEL_PATTERN`; on one line, labels separated by a single space are accepted only as the next letter in the run ("a. x b. y", not "Irene D. Amores"); on a line Word letters itself, a leading "H." is wording unless it repeats Word's own letter. PhpWord's reader HTML-escapes all text; `plainText()` undoes it. Changes here should be re-checked against real exam files, not only the tests.

## Tests

- Run them on a copy of the repo in a one-off offline container, sqlite in memory (phpunit.xml), so a test can never reach the dev database or the network. From WSL: `rsync -a --delete --exclude .git --exclude node_modules --exclude frontend --exclude ml/tools --exclude 'storage/framework/testing' --exclude 'storage/app/*' ./ ~/.cache/blis-test-copy/ && docker run --rm --network none -v ~/.cache/blis-test-copy:/app -w /app blis-system-php:latest php -d memory_limit=1G vendor/bin/phpunit` (add `--filter` for one file). About 790 tests, under a minute and a half.
- `tests/Unit/` holds one file per class with logic (services, machine learning, the Word parser's helpers, models, jobs, mail, rules, middleware); `tests/Feature/` drives the HTTP routes. New tests build their data with `tests/Support/BuildsBlisData.php` (`makeTeacher()`, `makeRoom()`, `makeBank()`, `makeExam()`, `makeSubmittedAttempt()` with one true/false/null per question, `makeBatteryExam()` and `makeBatterySitting()` for multi-subject exams answered per subject, ...), not their own copies of it.
- `JavaRandomTest`, `KnowledgeTracingServiceTest` and `LogisticModelTest` hold values worked out outside PHP (java.util.Random on JDK 17; per-exam Bayesian Knowledge Tracing in Python from the formula in `KnowledgeTracingService`'s docblock; WEKA 3.8.6's version 1 coefficients and predictions). If either fails, the code changed, not the expected numbers.
- Coverage: the PHP image has no coverage driver. Build one with PCOV on top of it (`FROM blis-system-php:latest`, `pecl install pcov`, `docker-php-ext-enable pcov`) and run phpunit with `-d pcov.enabled=1 -d pcov.directory=/app --coverage-filter=/app/app --coverage-filter=/app/routes`; the routes files are where much of the logic is, so leave them in. On 2026-10-14 this read 98.9% of statements. What is left is defensive code no request reaches (a temp file that cannot be created, a race between two checks), a few Word-list layouts, C4.5 subtree raising (checked against Weka by `ml/tools` instead).
